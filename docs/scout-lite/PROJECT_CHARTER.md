## 1. 一句话愿景

**把 Scout Lite 建成一款依托 Marauder 上游持续进化、在现有 ESP32-C5 硬件能力内功能尽可能完整、长期差异代码尽可能少、升级维护尽可能自动化的 PINGEQUA 固件产品。**

关键不是重新发明 Marauder，而是让 PINGEQUA 在有限工程资源下提供可靠、可升级、易使用、经得起长期维护的 Scout Lite 体验。

## 2. 商业目标与用户价值

### 2.1 产品定位

- Scout Lite 是面向 Flipper Zero / ESP32-C5 的 Wi-Fi、GNSS 与存储扩展硬件，不只是“可以刷官方二进制的 DevKit”。
- 保持 **Marauder 官方生态兼容** 为第一优先级；SigRoam FAP 应作为完善用户操作体验和 Wardriving 工作流的互补入口，而不再要求用户依赖独立的 SigRoam 固件才能发挥设备能力。
- 面向合规、授权的无线分析、Wardriving、GNSS 记录、数据导出与研究用途。
- 功能说明只承诺**在 Scout Lite 真实硬件上经测试的功能**，绝不笼统宣传“与官方最高端设备全功能完全一致”。

### 2.2 业务收益

1. 提高现有硬件的实际功能覆盖率，减少因“DevKit 目标缺功能”造成的体验差距。
2. 降低客户配置、升级、配套 FAP 使用的门槛，以及因 GPS/SD/Wi-Fi 使用误解造成的售后成本。
3. 建立可信的稳定固件、清晰变更日志、升级与回滚指南，使产品能够长期销售。
4. 尽可能把通用修复贡献至 Marauder 上游，降低 PINGEQUA 私有维护负担。
5. 把需要人反复处理的上游跟踪、差异比较、构建和初步测试转化为低成本自动流程。

### 2.3 可量化经营指标（先建立基线，不预设虚假数值）

- **功能可用率**：已验证通过的“硬件适用官方功能”项数 / 确认适用项数。
- **上游同步时延**：官方稳定版发布到产生可审查的同步 PR 的时间；成熟阶段目标为 3 个工作日内。
- **本地长期差异**：专用补丁项数、相对上游修改文件数、核心源码侵入点、需要人工解决的冲突数；观察趋势而非机械追求零修改。
- **发布质量**：稳定固件回滚次数、关键回归缺陷、构建重现率、长时间运行结果。
- **维护成本**：每次上游 Release 所需人工小时、AI/CI 费用、平均修复周期。
- **用户体验**：WiGLE 上传成功率、GPS 与 SD 相关售后问题、FAP 操作错误反馈。

## 3. 技术前提与非目标

### 3.1 已知硬件与产品边界

- 目标产品：PINGEQUA Scout Lite。
- 主控家族：ESP32-C5；硬件方案依据现有 Scout Lite PCB 与 C5 DevKit 的 Marauder 方案。
- 组成：ESP32-C5-WROOM-1U 模组、Quectel L86-M33 GNSS、microSD、外置双频 Wi-Fi 天线、USB-C、Flipper Zero UART/GPIO。
- 用户设计意图及附件记录主控规格为 N8R8；其 Flash、PSRAM 的实际识别、配置宏、分区布局、可用内存均待当前源码审计和实机检查确认。
- 现有 Scout Lite PCB 不以修改为第一阶段前提。所有“修固件即可解决”或“换目标固件即可刷入”的结论必须验证。

### 3.2 上游选择

- **唯一核心源码上游**：`https://github.com/justcallmekoko/ESP32Marauder`。
- **优先构建起点**：官方 ESP32-C5 DevKit 对应目标（构建 flag/产物命名以审计结果为准）。
- 截至本章程日期，官网最新正式标签可见 `v1.18.0`；下一次审计与升级必须动态检查最新 stable tag，不将该版本固化为永久目标。
- Marauder v8、Mini v3、Dual Mini C5 等**官方目标**可作为功能和实现对照；不得推定所有目标源码和依赖都可独立复刻。

### 3.3 明确不做

- 不重新编写 Marauder 主扫描引擎或全量替换框架。
- 不引入其他第三方固件作为 Scout Lite 的主固件基础。
- 不因单个新功能而整体移植其他设备的 UI、显示驱动、板级硬件抽象或大段无关逻辑。
- 不为“架构先进”而先做大规模重构、微服务化、插件平台或多仓库碎片化。
- 不把 Nightly 自动推送给正式客户，不允许无人工审核自动发布或自动刷写在售设备。
- 本项目不包含修改 PCB、增加屏幕、替换主控或推出第二代硬件；确有必要需另立项目并给出商业论证。

## 4. 长期技术原则（按优先级排序）

1. **Upstream first**：优先直接采用官方实现、配置、标准命令和已验证构建流程。
2. **Evidence before porting**：任何“缺失功能”须先定位是未实现、未开启、不可见、协议不兼容、硬件条件不足还是 Bug。
3. **Thin delta**：产品差异应尽量通过板级配置、受控扩展点和少量可审查补丁实现；不进行未经必要性证明的核心重写。
4. **Backward compatibility**：保持标准 Marauder CLI/Flipper 配套使用方式；保护 SigRoam FAP 已有工作流，变更协议须有兼容策略。
5. **Testable delivery**：编译通过不是功能通过；硬件依赖功能必须获得实机证据。
6. **Promote fixes upstream**：C5 通用 Bug、GPS/SD/上传通用修复优先推动上游接收；合并后逐步删除本地同等补丁。
7. **Automation with human gates**：机器自动发现、分类、构建、测试、建 PR；人类批准稳定版本合并与发布。
8. **Product truth**：功能矩阵、发布说明、Wiki/商详与固件实际能力一致，不以代码存在推断用户可用。
9. **Low operational overhead**：不增加本团队难以承担的永久基础设施和无意义周期性 AI 消耗。
10. **Security and legal compliance**：操作限定合法授权测试；不在仓库、CI 日志和 Agent 提示词中暴露客户凭据、WiGLE token 或敏感扫描数据。

## 5. 功能范围与优先级

> 以下均为**审计域**，不是声称目前缺失。每项必须登记：`上游路径/commit`、`构建宏`、`CLI/UI 可达性`、`外设前置条件`、`功能测试证据`、`处理结论`。

| 等级 | 功能域 | 审计/改进目标 | 初始策略 |
| --- | --- | --- | --- |
| P0 | 官方 C5 构建与分区 | 能从干净环境重复构建，并复现真实板的启动过程 | 复用官方工具链与构建脚本 |
| P0 | GPS 与 GNSS 数据流 | 初始化、Fix 状态、失锁恢复、时间戳、天线及 UART 配置 | 板级核实 + 实机测试 |
| P0 | microSD 与数据可靠性 | 卡检测、写入、日志格式、异常断电、无卡情况下安全退化 | 优先修复通用缺陷 |
| P0 | Wardriving | 2.4/5GHz 合法扫描、记录、状态切换、CSV/GPX（视上游支持） | 确认已有功能后最小补丁 |
| P0 | WiGLE / 其他官方上传流程 | 凭据、TLS、网络切换、上传失败重试、重复上传防护 | 先复现再定位，禁止假设不存在 |
| P0 | Flipper UART / SigRoam FAP | 标准 CLI 命令和响应、版本判断、持续兼容 | 协议合约测试 |
| P1 | 内存与资源管理 | Flash、PSRAM 使用、Wi-Fi 模式转换、任务生命周期、长时间运行 | 性能基线 + 针对性修复 |
| P1 | 官方其他 C5 功能 | 对比官方 v8、Mini v3 等目标，筛选无额外硬件依赖的实用功能 | 仅移植可独立验证的上游实现 |
| P1 | 设备恢复与升级 | 升级安全、回滚、出错后恢复、配置迁移 | 发布流程和验证 |
| P2 | SigRoam FAP 高级体验 | 可选能力协商、状态展示、清晰错误提示 | 单独评估 FAP 仓库改动 |
| P2 | 官网与 Web Flasher | 固件选择、兼容说明、升级/回滚文档 | 稳定固件成熟后推进 |
| P3 | 新产品功能 | 由销量、工单、社区反馈和实际工程成本决定 | 单独立项和验收 |

功能状态采用统一枚举：
- `CONFIRMED_WORKING`：当前 Scout Lite 实机通过。
- `SOURCE_PRESENT_UNTESTED`：源码存在，尚未验证可达/可用。
- `CONFIG_DISABLED`：存在实现但构建开关关闭。
- `INTEGRATION_BLOCKED`：硬件/接口/构建依赖不匹配。
- `BUG_REPRODUCED`：有可复现错误和日志。
- `PORT_REQUIRED`：在确认缺失并评估替代方案后才可登记。
- `NOT_APPLICABLE`：客观硬件不支持或不适用。
- `UNKNOWN`：信息不足，严禁推断。

证据等级：`E0=研究推断；E1=定位源码/官方文档；E2=构建或自动化协议测试；E3=台架实机测试；E4=长时间或实际使用验证`。稳定版 P0 项要求 E3，关键稳定性项还应有 E4。

## 6. 软件结构：可持续 Fork 而非另起炉灶

### 6.1 推荐三层逻辑

1. **Upstream Core**：Marauder 原生扫描、存储、网络、CLI、无线协议实现，修改应极少。
2. **Scout Lite Board Support**：与硬件绑定的 GPIO、UART、GPS、SD、分区、Flash/PSRAM、初始化顺序和构建目标。
3. **Scout Lite Extensions**：确实不能放在上游的设备状态、增强命令、SigRoam FAP 专属对接与产品级体验。

优先使用官方既有 board flag/feature flag/可扩展入口。**若为了实现三层逻辑反而需要重构大量上游代码，则先维持一个小型补丁集，不创建新的框架。**

### 6.2 跨项目协议边界

- 标准 Marauder CLI 是对外兼容基线：现有命令、响应、错误处理应尽可能原样保留。
- 如果新增 Scout Lite 专有控制能力，优先使用新命令命名空间，避免修改现有命令含义。
- 可选增加 `capabilities` 查询/版本协商，但必须先验证 SigRoam FAP 现状，不能擅自改动已有报文。
- 固件与 FAP 双仓库更新时，先定义兼容矩阵；固件应尽可能兼容旧 FAP，FAP 应对未知能力安全退化。

### 6.3 仓库及分支

- 以 GitHub 原生 Fork 关联 `upstream`，**不拷贝源码为无历史的新项目**。
- 只有一个 PINGEQUA Marauder 主 Fork；SigRoam FAP 保持自己的原仓库。
- `main`：稳定集成分支，禁止机器人直推。
- `feature/<topic>` / `fix/<topic>`：独立任务候选 PR。
- `upstream-sync/<version-or-sha>`：版本同步 PR，不作为永久分支。
- `release`/tags：仅对通过测试并人工批准的版本创建，保留对应二进制、构建日志与 SHA256。
- 版本建议为 `upstream-tag + pingequa-revision`，例如 `v1.18.0-pq.1`；正式命名需先确认不会与上游 Tag 冲突。

### 6.4 补丁台账

每项本地修改必须记录：`Patch-ID、原因、受影响文件、上游可用性、上游 PR 地址、测试、维护负责人/AI 任务、删除本地补丁的条件`。若上游合入等效修复，后续同步应清理重复补丁。

## 7. 与 Koko 上游的协作策略

- 通用修复优先提出小型、独立、可以复现的问题，提交 upstream Issue/PR；遵守贡献规范和第三方依赖许可。
- Scout Lite Board Target 作为可选上游贡献；是否被接受不得成为 PINGEQUA 项目的时间前提。
- 差异化产品功能尽量维护在独立模块；不将品牌专有设置硬塞进通用代码。
- 不从其他设备固件二进制逆向复制未公开代码来拼接功能。
- 对比官方机型时，区分公开源码中存在的能力、构建目标、硬件支持、特定商业机型构建限制。
- PR 的目标是**减少 PINGEQUA 的长期维护义务**，而不仅是增加上游贡献数量。

### 8.1 三条自动化通道（从少到多）

**通道 A — 轻量上游监控（第一批）**
- GitHub Actions 每日一次对比上游最新稳定 Tag 和最后已处理 SHA。
- 无变化时安静结束，避免启动 AI Agent。
- 有更新时生成唯一的 Issue 或同步候选 PR，标记来源 SHA 和影响范围。
- 同一上游版本只建一个活跃候选，防重复触发；网络/上游 API 错误不误判为无更新。

**通道 B — PR/CI 驱动的 Cursor Agent（第二批）**
- Project 订阅 `upstream-sync/*` 的新 PR 和关键 CI 失败。
- 分析变更对 C5、GNSS、SD、CLI、分区、存储、上传的影响；必要时建修复 PR。
- 若是 Nightly 更新，默认只研究和生成报告，不合入正式分支。
- 复核每次订阅是否和外部 Cursor Automation 重叠，避免重复任务与重复计费。

**通道 C — 可选硬件回归（第三批）**
- 使用一台专门的 Linux/Mac 台架主机和可替换测试样板；USB/串口/电源重置能力按真实设备逐步实施。
- 烧录前检查设备标识、固件 hash 和完整刷机布局；对未知分区布局不盲目烧录。
- 记录串口日志、测试结果、环境、SD/GPS 条件、可复现步骤；只在沙箱/测试设备执行。

### 8.2 Agent 成本与运行纪律

- 初始最多同时运行 2 个独立子任务 Agent；串行优先，任务可并行时才并行。
- 监控采用脚本触发，AI 只处理发生变化的差异；禁止每天无条件全仓库“深度审查”。
- 提交前先列出改动范围、风险和验证计划；改动核心模块或分区表需特别审查。
- 每月回顾 AI 费用、重复 Agent 任务、无效 PR，调整触发条件。

## 9. 测试与质量门禁

### 9.1 阶梯式质量门禁

| 门禁 | 用途 | 结果要求 |
| --- | --- | --- |
| G0 源码审计 | 功能归类、上游证据、影响分析 | 每个结论提供路径/commit 和证据等级 |
| G1 可重复构建 | C5 目标和工具链 | 干净环境成功、记录依赖版本和构建 hash |
| G2 自动协议回归 | CLI 兼容、FAP 交互、日志解析 | 核心命令输入输出测试通过 |
| G3 实机台架 | Wi-Fi、GNSS、SD、WiGLE、Flipper | P0 硬件相关项达到 E3 |
| G4 长稳/异常 | 断电、无卡、失锁、连接失败、资源泄漏 | 关键流程恢复合理，有故障日志 |
| G5 产品放行 | 变更说明、升级说明、回滚与批准 | 人工审批后发布 stable |

测试至少覆盖：启动与版本读回、分区匹配、UART 波特率和引脚、卫星定位与 No-Fix、2.4/5GHz 扫描、SD 正常/拔卡、CSV 可导入性、上传成功/失败/重复、Wi-Fi 模式切换、内存趋势、长时运行、旧版 SigRoam FAP、升级与回退。

谨慎对待附件中“无 Fix 记录应当写成 No Fix”“驻留时间默认值”“上传命令名称”等具体断言；应以源代码协议及用户可重现实测建立用例。

### 9.2 发布级别

- `audit`：仅研究资料或测试编译；不对客户发布。
- `nightly-internal`：基于上游 master 或未完成审计的候选；仅研发台架。
- `beta`：主要功能测试通过，有明确已知限制；仅可控试用。
- `stable`：通过 G1–G5，产品文档匹配，有升级/回滚操作指导。

稳定版资产至少包含：`firmware.bin` 或官方要求的一组烧录产物、所用 commit SHA、上游 Tag、工具链版本、构建参数/分区文件、SHA256、变更说明、兼容矩阵、已知问题与回滚方式。

## 10. 路线图：按门禁推进，不死守日期

> 时间仅为规划窗口，用户当前的审计正在进行，应以实际技术风险和可验证成果决定推进节奏。

### M0 — 接管现有审计（现在进行中）

**交付**：确认 Cursor 已经运行的任务、commit/tag、报告、PR、构建脚本、未解决问题，建立当前事实台账与 `PROJECT_STATUS.md`。

**退出门禁**：不存在重复审计；产品硬件信息的已知/未知边界清楚；至少形成一份可追溯的差异报告草案。

### M1 — 可复现官方基线与功能矩阵（近期）

**交付**：官方 C5 固件可重现构建；主要功能逐项分类；明确真实缺陷列表和“不需要修改即可使用”的功能。

**退出门禁**：所有 P0 功能至少有源码证据；不可实测项标明原因及待测动作。

### M2 — 最小可用 Scout Lite 固件（第一交付）

**交付**：最小 Board Target/配置补丁、关键 Bug 修复、原生 CLI 与 SigRoam FAP 回归、初版 Beta。

**退出门禁**：P0 核心功能在实机获得证据，且本地 diff 与上游合并成本可接受。

### M3 — 首个稳定产品版（中期）

**交付**：稳定固件、Flasher/下载指导、双语 Wiki、完整变更日志、回滚方案、客户支持清单。

**退出门禁**：G1–G5 满足、产品声明与实际功能一致、真实用户关键工作流可复现。

### M4 — 自动化升级与上游回馈（中期）

**交付**：Release 监控、候选同步 PR、Cursor 订阅、自动差异分析/构建、第一批适合 upstream 的通用 PR。

**退出门禁**：模拟一次新的上游 Release，可在不打断 stable 的情况下完成候选 PR 和测试报告。

### M5 — 维护成熟期（长期）

**交付**：受控硬件测试台架、定期维护费用报告、补丁清理机制、用户反馈驱动的新功能计划。

**退出门禁**：多次上游版本升级后，人工操作量不随累计修改显著增长；回滚与兼容性流程得到真实演练。

### 12–24 个月产品演进视角（滚动规划，非承诺日期）

| 时间视角 | 重点投入 | 可见产品成果 | 放弃或推迟条件 |
| --- | --- | --- | --- |
| 0–2 个月 | 完成在途审计、构建基线、P0 关键功能验证 | 功能矩阵与内部 Beta，可复现安装/回退 | 基础构建或实机问题未定位时不扩功能 |
| 2–6 个月 | 稳定版、FAP 兼容、上游 PR、同步候选流水线 | 可面向客户说明的稳定固件与维护日志 | 不为堆功能牺牲升级可靠性 |
| 6–12 个月 | 受控硬件回归、客户反馈归因、自动化优化 | 官方更新后能以较低人工成本形成可测试候选 | 自动 Agent 成本高于人工价值时收缩范围 |
| 12–24 个月 | 长期补丁清理、能力复盘、产品二代可行性评估 | 低差异的成熟固件；如确有需求才评估硬件升级 | 当前硬件仍有性价比时不为追新更换主控 |

以上时间窗口需要以当前 Cursor 审计产出重新估算。绝不为达成时间表而绕过测试或扩大上游分叉。

### 长期节奏

- 每个上游稳定 Release：自动建立一次候选差异与风险评估。
- 每周：低成本汇总阻塞事项、开放 PR 和审计发现；仅有变更才调动代码 Agent。
- 每月：产品/售后问题归类、维护成本回顾、上游补丁状态和下一期重点审定。
- 每季度：审查架构债务、核心 diff、已废弃扩展、功能优先级，不以“功能数量”替代价值判断。

## 11. 决策与任务治理

### 11.1 每个需求必须回答的问题

1. 用户到底要解决什么问题？真实证据是什么？
2. 官方是否已经实现？在哪个版本和源码路径？
3. 是否只是构建宏、硬件定义或 FAP 呈现路径的问题？
4. 是否存在无代码解决方案？
5. 最小修改是什么？是否能提出 upstream PR？
6. 对 ESP32-C5 内存、Flash、网络/存储资源和 CLI 有何影响？
7. 哪些自动测试能覆盖？哪些必须实机？
8. 如何回退？版本和日志如何追踪？
9. 后续每次上游更新维护它需要多少成本？

### 11.2 ADR（Architecture Decision Record）

对重大变更写简短 ADR，包含：背景、备选方案、选型理由、被放弃的方案、性能/维护影响、验证与回退。需要 ADR 的变更包括：编译系统迁移、核心模块重构、分区布局改变、CLI 兼容性破坏、依赖替换、新硬件要求、引入自动烧录、自动发布。

### 11.3 项目状态必须独立维护

`PROJECT_STATUS.md` 至少记录：最近更新日期、当前 M 阶段、最新验证的 upstream SHA、最近合并的 PINGEQUA SHA、审计进度、阻塞项、活跃 PR、下一步 3 个最优先任务、谁负责、验证证据和风险。

状态报告不得写“已修复”却没有 commit、PR 或测试证据；不能用 AI 的自我评价替代质量门禁。

## 12. 风险台账

| 风险 | 后果 | 控制策略 |
| --- | --- | --- |
| 官方 C5 原已有功能却被重复开发 | 维护量扩大且引入回归 | 功能矩阵与 E1/E2 证据先行 |
| 上游频繁变更核心接口 | Fork 冲突积累 | 薄补丁、隔离专属功能、上游 PR |
| GPS/SD/PSRAM 配置被猜测 | 启动失败、数据损坏 | 核对原理图、实机和构建产物 |
| Nightly 直接进入正式版本 | 不稳定固件影响客户 | stable 候选 PR 与人工 G5 |
| Cursor 递归触发多个自动 Agent | 费用和 PR 噪音 | 去重键、最多两并行、超时/配额 |
| 构建绿灯但实机失败 | 错误交付 | 硬件 E3/E4 测试不可省略 |
| 分区/bootloader 切换不当 | 刷写失败与数据丢失 | 产物完整性、升级指南、回滚验证 |
| CLI 不兼容 SigRoam FAP | 老客户失去功能 | 合约测试、能力协商兼容策略 |
| 密钥/扫描数据泄漏 | 用户隐私和安全风险 | Secret 管理、样例数据脱敏、最小权限 |
| 上游不接受 Board Target | 本地维护成本持续 | Board 补丁独立、可重放、不阻塞发布 |

## 13. 下一步给正在运行的 Cursor Project 的执行要求

**立即要做的是文档接管，不是重新启动源码审计。**

1. 识别现有正在运行的 Scout Lite 审计任务和工作分支/PR。
2. 读取本章程，先指出与已有成果矛盾的内容，但不得擅自抹掉已有证据；将争议记录为 `Decision Pending`。
3. 保存章程到 `docs/scout-lite/PROJECT_CHARTER.md`，建立精简 `AGENTS.md` 和 `PROJECT_STATUS.md`。
4. 依据已有审计输出更新功能矩阵；无验证项目保留 `UNKNOWN`。
5. 提供后续 3 个最划算的任务与依赖关系；不要将全部路线图一次性派发给多个 Agent。
6. 文档维护 PR 与当前研发 PR 尽量隔离；未经授权不要覆盖现有分支或自动合并。
7. 每次完成任务更新项目状态，长期不需要重新解释项目愿景。
