# PINGEQUA Scout Lite Marauder 专用固件项目需求 V1.0

## 1. 项目定位

本项目旨在基于 JustCallMeKoko 官方 ESP32 Marauder，为 PINGEQUA Scout Lite 建立一套长期可持续维护的专用固件。

本项目不重新开发 Marauder 核心，不采用其他第三方固件作为基础，也不以某个第三方设备的固件作为替代品。

**核心目标：在现有 Scout Lite 硬件允许范围内，最大限度实现 Marauder 官方功能完整性，同时最小化对上游代码的长期维护负担。**

## 2. 硬件基础

目标硬件为现有 PINGEQUA Scout Lite：

- ESP32-C5-WROOM-1U-N8R8
- Quectel L86-M33 GNSS
- microSD 卡槽
- 2.4GHz / 5GHz Wi-Fi
- 外置 Wi-Fi 天线
- Flipper Zero GPIO / UART 通信接口
- USB-C

当前硬件按照官方 C5 DevKit Marauder 方案设计。

项目第一阶段不以重新设计 PCB 为前提。所有硬件和固件资源定义均需通过 Scout Lite 实际原理图、官方资料及测试验证。

## 3. 技术基线

- 上游仓库：justcallmekoko/ESP32Marauder
- 默认目标：MARAUDER_C5 / ESP32-C5-DevKitC-1
- 初始稳定版候选：v1.18.0
- 保留历史已验证固件作为对照和回滚基线
- 其他官方 C5 构建目标作为功能比较对象，不直接混用二进制固件

## 4. 主要研发任务

### A. 完整功能审计

对官方 Marauder 各相关构建目标进行功能与源码级比较。

重点涵盖：

- 2.4GHz / 5GHz Wi-Fi 功能
- BLE 功能
- Wardriving 及日志生成
- GPS 数据、定位状态和轨迹管理
- SD 存储和文件管理
- WiGLE / WDGWars 数据上传
- Wi-Fi 网络连接与配置文件管理
- 设备状态、内存、错误恢复
- CLI / UART / Flipper 通信
- 其他可由现有 C5 硬件支持的官方功能

逐项明确源码位置、编译开关、硬件依赖、运行条件以及是否真正缺失。

### B. 最小侵入式功能完善

按照以下顺序选择实现方式：

1. 直接启用官方已有功能。
2. 修正板型配置或初始化错误。
3. 修复官方 C5 通用 Bug。
4. 复用官方其他目标中已经公开的成熟实现。
5. 最后才开发 Scout Lite 独有的新代码。

不能因为功能在某个构建目标中不可用，就未经审查直接复制其他机型的大段代码。

### C. 长期维护架构

建立 PINGEQUA 官方 Fork。

以较小的 Scout Lite Board Support 层和独立扩展模块实现差异化。

要求：

- 尽量不修改 Marauder 核心逻辑。
- 不引入不必要的框架或构建依赖。
- 保持标准 CLI 兼容。
- 兼容现有 SigRoam FAP。
- 明确协议版本与能力协商机制。
- 每个产品补丁具有明确用途和测试证据。
- 上游接受的通用修复从本地补丁集中移除。
- 严格控制后续上游合并冲突成本。

### D. 上游贡献策略

通用 Bug、可复用功能增强、安全性与稳定性修复，优先提交上游 PR。

Scout Lite 板型支持争取纳入官方目标。

PINGEQUA 专属品牌配置、专用协议和差异化功能原则上独立维护。

在提交 PR 前审查官方贡献规则、相关许可、测试要求以及已有解决方案。

### E. 自动化维护系统

基于 GitHub Actions、脚本、Cursor 及适当的 AI 编程代理建立更新流程。

系统应能够：

- 定期检查 Marauder 版本和代码变化。
- 比较上游与本地代码差异。
- 对更新进行功能分类和影响分析。
- 自动生成可审查的维护任务或 PR。
- 在可控条件下辅助合并和修复代码。
- 自动编译 Scout Lite 固件。
- 运行静态检查、单元测试和协议测试。
- 连接真实硬件时执行自动化实机验证。
- 生成版本变更日志、SHA256 和测试报告。
- 人工批准后发布正式固件。
- 保存已验证版本，支持回滚。

AI 不能未经审核自动部署有风险的生产固件。

### F. 质量与安全要求

重点验证：

- Wi-Fi 工作模式切换与资源释放
- GNSS 定位有效性及时间同步
- SD 写入可靠性与异常断电恢复
- WiGLE 上传失败重试及状态一致性
- 内存泄漏、堆栈占用和 PSRAM 使用
- Flipper UART 命令兼容性
- 固件升级、分区和版本回滚
- 凭据存储及敏感信息保护
- 长时间运行稳定性
- 合法授权环境中的无线功能合规性

## 5. 研发交付物

项目应提供：

1. **Marauder 官方功能与 Scout Lite 兼容性审计报告**
2. **功能差异及优先级矩阵**
3. **Scout Lite 专用固件架构设计**
4. **最小修改方案与上游 PR 规划**
5. **自动化维护和 CI/CD 设计**
6. **实机测试矩阵和验收标准**
7. **固件版本管理、发布和回滚规范**
8. **开发任务清单与后续维护成本评估**

## 6. 研发决策原则

- 开发效率高于不必要的架构复杂度。
- 官方现成实现优于自行重新开发。
- 上游通用方案优于长期私有补丁。
- 可验证的功能完整性优于表面功能数量。
- 长期自动化维护能力优于一次性完成度。
- 稳定性和标准协议兼容优于未经验证的功能扩张。

## 7. 最终验收目标

交付一套在 Scout Lite 实际硬件上经过验证、保留 Marauder 标准兼容能力、具备清晰产品差异、能够持续接收官方更新的专用固件。

下一次 Marauder 官方更新时，应尽可能通过自动化流程完成代码审查、集成候选生成及大部分测试，而不是重新人工研究和移植整套固件。

**最终要求：功能尽可能完整、代码差异尽可能小、长期维护尽可能自动化。**
